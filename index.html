// Fundamentals

Cloud identity, in three dialects

Every cloud attack path ultimately runs through an identity primitive. Know the vocabulary before the techniques make sense.

AWS

IAM — users, roles, policies

Account → IAM → STS
  • sts:AssumeRole is the trust primitive — cross-account access runs through it
  • Identity-based policies on principals, resource-based policies on resources (S3, KMS, Lambda)
  • iam:PassRole + a compute service = the single most common privesc primitive in AWS
  • Instance metadata service (IMDS) hands out temporary creds to anything that can reach 169.254.169.254
  • Policy evaluation: explicit deny always wins, otherwise any allow at any layer (identity, resource, SCP, permission boundary) is required to pass
Azure

Entra ID — RBAC + Managed Identity

Tenant → Subscription → Resource Group
  • Azure RBAC controls resources; Entra ID roles control the directory itself — attackers conflate them, defenders shouldn't
  • Managed Identities (system or user-assigned) are Azure's answer to IMDS — reachable at 169.254.169.254/metadata/identity
  • Service principals + app registrations are the automation identity layer — often over-permissioned and rarely rotated
  • Owner or Contributor + a VM/Function = role assignment write → impersonate the resource's identity
  • Conditional Access evaluates per sign-in — token theft and device-code phishing both sidestep it
GCP

IAM — service accounts rule everything

Org → Folder → Project
  • Service accounts are both identities and resources — you can grant a user permission to act as one
  • iam.serviceAccounts.actAs / getAccessToken is GCP's version of PassRole
  • Metadata server at metadata.google.internal serves SA tokens to any workload on the VM/GKE node
  • Roles are bundles of permissions; primitive roles (Owner/Editor/Viewer) are blunt and still common in older projects
  • Org Policy constraints are the GCP equivalent of SCPs — frequently unset at the org root
// Identity abuse

Privilege escalation paths

Cloud privesc is rarely a software bug — it's a legitimate permission used in an order its grantor didn't picture.

AWSHigh value

PassRole + service launch

Holding iam:PassRole plus permission to launch EC2, Lambda, or Glue lets you attach a privileged role to a resource you control, then pull its temporary credentials.

  • Enumerate: which roles can this principal pass? Which launch actions does it hold?
  • Classic chain: PassRole → lambda:CreateFunction → invoke → steal creds from the function's execution environment
  • Tools: Pacu, PMapper, cloudsplaining for static policy graphing
AWS

Policy / permission-boundary edit

Any principal with iam:CreatePolicyVersion, iam:AttachUserPolicy, or write access on its own permission boundary can self-escalate directly.

  • ~20 known IAM privesc vectors cataloged by Rhino Security Labs — still the reference list
  • iam:PutUserPolicy on self = instant admin if unrestricted
  • Detect: CloudTrail PutUserPolicy / AttachRolePolicy from a principal that shouldn't touch IAM
AWS

Confused deputy via resource policy

A resource policy (S3 bucket, SQS queue, Lambda) that trusts a role without a source condition lets any account using that role reach the resource — including one that isn't the intended caller.

  • Mitigation: aws:SourceArn / aws:SourceAccount condition keys on every cross-service trust
  • Common in S3 bucket policies written to "just work" across accounts
AzureHigh value

Managed Identity token theft

Code execution on any VM, App Service, or Function with a Managed Identity attached can request a token for that identity directly from the metadata endpoint — no credential needed.

  • curl -H "Metadata:true" "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2024-02-01&resource=https://management.azure.com/"
  • SSRF on an app with a Managed Identity = instant token exfil
  • Tools: ROADtools, Stormspotter, AzureHound
Azure

Role assignment write

Microsoft.Authorization/roleAssignments/write on a scope lets a principal grant itself (or a controlled identity) Owner at that scope — the Azure equivalent of self-granted IAM policies.

  • Often bundled inside custom roles meant only for "assign reader access"
  • Chain: Contributor on a VM → attach a user-assigned Managed Identity with Owner → extract its token
Azure

App registration / service principal abuse

Owning an app registration lets you add credentials (client secret or certificate) to it directly — if that app has elevated Graph or RBAC permissions, you inherit them silently.

  • Application.ReadWrite.All Graph scope = add yourself as owner on any app, then add a secret
  • Dormant high-privilege service principals are a common finding in access reviews
GCPHigh value

actAs + service account impersonation

A principal with iam.serviceAccounts.actAs on a service account can deploy a resource that runs as it — or call generateAccessToken directly if that permission is also granted.

  • Chain: Editor on a project → deploy a Cloud Function as a privileged SA → invoke → exfil token
  • Tools: GCPwn, G-Scout, Cartography for IAM graph mapping
GCP

Primitive role sprawl

Legacy roles/editor grants carry hundreds of permissions including most of IAM — a single over-broad grant from early project setup often outlives every later hardening pass.

  • Editor includes iam.serviceAccounts.actAs on most SAs by default
  • Audit: gcloud projects get-iam-policy + flag any primitive role bindings
GCP

Metadata server SSRF

Any SSRF-capable app on a GCE instance or GKE node can read the attached service account's token from metadata.google.internal without authentication — the GCP analog of IMDS abuse.

  • curl -H "Metadata-Flavor: Google" "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"
  • GKE nodes without Workload Identity expose the node's SA to every pod on it

Attack flow chains

Individual primitives rarely matter alone — these are the chains that turn a small finding into account takeover.

App-layer SSRF→ request 169.254.169.254→ IMDSv1 role creds→ enumerate permissions→ PassRole / S3 read→ pivot account
Public S3 write → static site takeover → credential harvest
bucket ACL/policy public-write→ overwrite hosted JS→ inject credential-stealing script→ visitor session/token capture
Leaked CI secret → registry push → supply-chain compromise
secret in repo / CI logs→ registry push creds→ poison base image→ downstream builds pull it→ RCE in consuming environments
Container escape → node compromise → cluster-wide pivot (K8s)
privileged / hostPath pod→ break out to node→ read kubelet creds→ list secrets cluster-wide→ cloud SA token on node→ pivot to cloud control plane
Overprivileged Lambda role → event injection → data exfil

GKE Workload Identity gap → pod to project takeover
pod without Workload Identity binding→ inherits node default SA→ read node SA token from metadata→ node SA often has Editor→ project-level compromise
OIDC trust misconfig → GitHub Actions → cloud role assumption
OIDC trust policy too broad→ any repo/branch can assume role→ fork PR triggers workflow→ workflow assumes cloud role→ attacker-controlled code gets cloud creds
// Runtime

Container & Kubernetes attacks

The orchestration layer sits between workload and cloud — a weak boundary here reaches both.

K8s

Privileged pod escape

A pod running with privileged: true or a mounted hostPath of / can chroot or mount the host filesystem directly — full node compromise from a single manifest flaw.

K8s

Exposed kubelet API

Kubelet's read-only port (10255) or unauthenticated 10250 lets an attacker on the pod network list pods/secrets or execute commands directly via /run and /exec endpoints.

K8s

Overpermissive RBAC

A ServiceAccount bound to cluster-admin for convenience turns any compromise of that pod into full cluster control — the single most common finding in K8s audits.

K8s

Exposed dashboard / etcd

An internet-reachable Kubernetes Dashboard or unauthenticated etcd (port 2379) hands over cluster secrets and workload control with no exploit required.

K8s

Malicious admission webhook / image

A compromised registry or unpinned :latest tag lets an attacker swap an image between build and deploy — the cluster pulls and runs it trustingly.

K8s

Secrets as env vars

Secrets injected as environment variables are readable by any process in the container and often leak into crash dumps, logs, and /proc/[pid]/environ.

// Event-driven compute

Serverless attack surface

No server to patch doesn't mean no attack surface — the function's identity and its triggers are the new perimeter.

Lambda

Over-privileged execution role

Functions are routinely granted broad roles during development and never trimmed — a single injected payload inherits everything the role can do.

Lambda

Dependency / layer poisoning

A compromised Lambda Layer or a typosquatted package pulled at build time executes with the function's full IAM role on every invocation.

Lambda

Event-source injection

Functions triggered by S3, SQS, or API Gateway often trust the event payload structure — malicious input (deserialization, path traversal, SSRF) reaches application logic without any auth step.

Functions

Function key leakage

Function-level and host-level keys grant invoke access and sometimes admin API access — frequently hardcoded in client apps or leaked in logs.

Cloud Run / Functions

Unauthenticated invoker

Cloud Run services deployed with --allow-unauthenticated for convenience during testing are a common finding left in production, exposing the service's attached SA to the internet.

All

Cold-start credential caching

Credentials cached in a warm execution environment can persist across invocations from different tenants of the same function if isolation assumptions are wrong — rare, but high impact when found.

// Build pipeline

CI/CD & software supply chain

The pipeline holds more privilege than the production environment it deploys to — attackers increasingly target the build, not the runtime.

OIDC trust policy too broad

A cloud role trust policy scoped to an entire GitHub org instead of a specific repo/branch lets any workflow — including one in a forked PR — assume it.

Secrets in pipeline logs

Build logs that echo environment variables or command output leak cloud credentials, registry tokens, and signing keys to anyone with log read access.

Self-hosted runner compromise

A self-hosted CI runner persists state between jobs — one malicious job can plant a backdoor that every subsequent job on that runner inherits.

Dependency confusion

Publishing a public package matching an internal package's name can trick misconfigured build tooling into pulling the attacker's version instead.

Unsigned artifact promotion

Without artifact signing and provenance (SLSA, Sigstore/cosign), nothing stops a compromised registry step from substituting a malicious build between stages.

Terraform state exposure

State files stored in a misconfigured backend bucket often contain plaintext secrets and full resource topology — a complete attack map handed over for free.

// Data layer

Storage & data exposure

Still the most common finding in every cloud security assessment, and still the one with the simplest fix.

S3

Public bucket / public ACL

Block Public Access disabled at the bucket or account level, combined with a permissive bucket policy, exposes objects directly — still found via simple bucket-name guessing.

Blob

Anonymous container access

Containers set to "Blob" or "Container" public access level serve data with no authentication — SAS tokens with no expiry compound the exposure.

GCS

allUsers / allAuthenticatedUsers IAM binding

Granting allUsers read on a bucket is the GCP equivalent of a public S3 bucket — easy to set during a demo, easy to forget to remove.

Unencrypted snapshots shared publicly

EBS snapshots, Azure managed disk snapshots, and GCP disk images marked shareable across accounts leak full filesystem contents, including credentials at rest.

Database exposed to 0.0.0.0/0

RDS, Azure SQL, and Cloud SQL instances left reachable from any IP rely entirely on credential strength — a single leaked password becomes direct data access.

Backup target neglect

Backup vaults and cross-region replicas are often excluded from the same monitoring and access review applied to primary data stores.
